# 评测提速优化 · 立项计划（任务处理速度，结果等价）

> 2026-11-23 立项。500 题单轮递增评测耗时约 17 小时，瓶颈是 ~10,800 次**串行**模型调用。
> 目标：在不改变评测结果语义的前提下大幅提速。本文只做计划，不实施。

## 一、耗时结构（实测）

| 指标 | 数值 |
|---|---|
| 每题消息数（=写入调用数） | 平均 21.6 条（500题约 10,800 次写入调用） |
| 加上答题调用 | 每题 22.6 次，500 题约 11,300 次 |
| 实测速度 | ~28 题/小时 → 500 题约 17-18 小时 |
| 每次调用固定开销 | 新建 SuanliAdapter + GatewayModelProvider + YoAiAgent + ToolRegistry |

**结论**：慢不是模型一次调用慢，是**调用次数多且全串行 + 每次重建对象**。

## 二、优化方向（按"等价性风险"从低到高分四层）

### L0 · 零风险：对象复用 + 连接复用（不改语义）
- 现状：每条消息 new 一个 adapter/agent/registry，重复初始化。
- 优化：每题复用一个 GatewayModelProvider 实例（只换 prompt），HTTP 连接池复用。
- 等价性：**完全等价**——同一模型、同一 prompt、同一温度，只是不重建对象。
- 预期收益：单次调用省去初始化开销，约 5-15%。

### L1 · 低风险：题内写入并发（保持写入顺序）
- 现状：一条消息 await 完才写 memory，再写下一条。
- 优化：**模型抽取阶段并发**（N 条消息的抽取调用并行），但**写入 memory 严格按原顺序**串行 append。
  关键点：抽取调用只读单条消息、彼此独立；只有写 memory 有顺序依赖（event_time/topics 关联）。
- 等价性：**语义等价**——模型看到的输入、每条抽取结果都相同，写入顺序也相同；
  唯一差异是并发下模型服务的响应可能有微小随机性（本来 run 间就波动 ±12pp，这是既有噪声）。
- 预期收益：题内 21.6 次串行 → 一批并发，**单题从分钟级压到秒级**，整体 5-10×。
- 风险点：网关并发限流（需测最大并发数，先试 4-8 路）。

### L2 · 低风险：题目间并发（多题并行）
- 现状：题目串行 for 循环，每题 asyncio.run 一次。
- 优化：改成单个 async 主循环，多题并发（如 4-8 题同时跑），每题独立 case_dir/tmem 不共享状态。
- 等价性：**完全等价**——题目之间无任何共享状态，各自 memory 独立。
- 预期收益：与 L1 叠加，理论上 500 题可在 1-2 小时内跑完。
- 风险点：并发总请求数 = 并发题数 × 题内并发数，需控制总量不触发限流。

### L3 · 中风险：评分（judge）并发
- 现状：评分 500 次 judge 调用串行（temperature=0）。
- 优化：judge 调用并发（temperature=0 无随机性，完全确定）。
- 等价性：**完全等价**——judge 无状态、temperature=0。
- 预期收益：评分从 7-13 分钟压到 1-2 分钟。

## 三、不做的事（保证结果不变）

- ❌ 不减少模型调用次数（会破坏"逐条递增"这一生产形态语义）
- ❌ 不改 prompt / 温度 / seed（改动会改变抽取内容）
- ❌ 不改 judge prompt / 模型（评分口径必须一致）
- ❌ 不缓存答题结果（每轮独立运行才能反映真实随机性）

## 四、验证方案（等价性必须先证明）

任何一层优化落地前，必须做**同题对照**：
1. 用同一批 30 题，分别跑"原始串行版"和"优化并发版"；
2. 逐题对比：写入记忆条数、触发率、答案文本、judge 分数；
3. 判定标准：**分数差异在既有 ±12pp 运行间波动范围内**，且无系统性偏差
   （不能出现"优化版恒定低于原版"）；
4. 若等价 → 采纳并设新默认值；若不等价 → 回退并记录原因。
