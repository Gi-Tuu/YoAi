# 单轮低温记忆抽取 · 生产可行性验证

> 2026-11-22。用户问"现状能用吗"→ 发现 +8.8pp 低温收益只在评测侧，没进生产。
> 用户提出"智能调温"，建议先做 A（记忆抽取低温分流）→ 核实后发现生产没有独立记忆调用
> → 用户选"先做单轮抽取可行性验证"。本文是验证结论。

## 一、架构核实（为什么不能简单"改个参数"）

1. **生产侧无独立记忆调用**：`remember_event` 是主对话 loop 里的工具，
   模型在生成回答时顺带调用——记忆抽取与对话共用同一次 achat、同一 temperature。
2. **评测的 +8.8pp 来自生产不存在的步骤**：`_memory_phase_model` 是单独一次低温调用、
   批量抽取整段历史（haystack）。生产链路没有这个前处理步骤。
3. 所以"低温进生产"不是改参数，而是要新增一次 LLM 请求（延迟代价）+ 确保工具触发。

## 二、单轮可行性实验（不改生产代码）

`bench/probe_singleturn_memory.py`：10 条带明确事实的单轮用户消息，
对比 temperature=默认(None) vs 0.1，统计触发率、抽取条数与正确性。

| 指标 | 默认温度 | 温度 0.1 |
|---|---|---|
| 工具触发率 | **10/10** | **10/10** |
| 抽取事实总数 | 19 | 18 |
| 平均条数/消息 | 1.9 | 1.8 |
| 内容正确性 | 数字/名字/时间/偏好均逐条记对 | 同左 |

**关键发现 1**：单轮输入能稳定触发 remember_event（10/10）——
之前实验记 0 条是我用了英文短 prompt；复刻评测的中文 prompt 后正常。
抽取质量高：$12,000、1992-03-15、three kids、oat milk、5 miles 全部逐字记对。

**关键发现 2**：**单轮场景下默认温度与 0.1 几乎无差别**（19 vs 18 条，内容一致）。
原因：低温解决的"认真/敷衍模式随机跳"**只在批量长历史时出现**（一次看 20+ 条输入），
单轮短输入（一句话）本来就不会触发模式跳。

## 三、结论（诚实，避免无谓改动）

- **单轮抽取可行**：触发稳定、事实准确——如果将来要给生产加记忆前处理，技术上没问题。
- **但低温在单轮无收益**：+8.8pp 是"批量历史回放"场景的收益，生产的单轮输入本来就没有
  "模式随机跳"问题。给生产加低温前处理 = 多一次 LLM 请求（延迟）+ 零收益。
- **"智能调温"的前提不成立**：至少在记忆写入这件事上，单轮不需要调温，默认就够好。
  对话侧是否温度敏感（高温=更自然）仍未验证，但那是另一个问题，且没有数据显示需要调。
- **决策**：不新增生产记忆前处理步骤，不改生产温度。+8.8pp 明确标注为
  "批量历史回放场景（评测口径）的收益，生产单轮场景不适用"。

## 四、这也解释了为什么评测与生产有差距

评测用 LongMemEval 的 haystack 一次性喂 10-20 条历史（批量回放），
生产是用户一次说一句话（单轮递增）。两者的记忆写入机制本质不同：
- 批量：模型一次看全部，需低温防止"敷衍摘录"→ 低温 +8.8pp
- 单轮：模型每次看一句，天然稳定 → 无需调温

这不是 bug，是评测协议与真实使用的差异。要严谨评估生产记忆质量，
应该用"单轮递增写入 + 后续检索"的协议，而不是批量回放——这是未来评测改进方向。
