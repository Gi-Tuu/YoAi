# 进化对照实验：全链路缺口审查与收敛方案

> 2026-11-22。用户在 A/B/C/D 对照实验中选"给专家真实能力差异"后，
> 我对进化机制做了一次全链路审查，发现骨架完整但血肉未通。本文一次讲清缺口、
> 改造方案、工作量与降级选项，供一次性拍板，避免逐层试错。

## 一、现状：M0-M2 骨架都在，但三处"未接线"

| 环节 | 代码状态 | 真实缺口 |
|---|---|---|
| M0 进化档案 | 已实现，13 测试 | ✓ 无缺口 |
| M1 专家路由 | 已实现，14 测试 | 按指纹选专家，但**专家之间只有 prompt_suffix 差异** |
| 专家能力配置 `ExpertSpec.tools` | 字段存在 | **不生效**：`ExpertModelProvider` 执行时未按白名单过滤工具，tools 只用于路由打分 |
| M2 归因/候选/晋升 | 已实现，12 测试 | `BenchmarkLab` 要父子成对验证样本，链路没产出这种结构 |
| 验证样本入口 | 本轮已补（0→120 条） | 但缺父节点对照，每个标签边界 parent_items=0 → 仍 insufficient |

**四组 30 题冒烟结果**：A/B/C/D 全部 20/30 = 66.7%，完全一样。
原因：专家只换提示词，对纯记忆 QA 的对错没有实质影响——路由选谁都一样。
**这是"当前专家配置没有可测路由收益"的诚实信号，不是评测 bug。**

## 二、收敛改造方案（三步，做完才能测出真收益）

### 步骤 1：让专家白名单真正生效（根）
- 在 `YoAiAgent` 加每次 `astream` 前的工具过滤 hook：向 provider 查询"本次专家允许的工具集"；
  `ExpertModelProvider` 根据 `last_decision` 选中节点的 `spec.tools` 返回白名单。
- 专家设计成**实质差异**：
  - `memory_expert`：白名单含 `remember_event`/`events_between`/`summarize_theme`（能查时间记忆）
  - `research_expert`：白名单含聚合工具
  - `root`：空白名单（裸答）
- 改造在 YoAi 内（`src/yoai/`），不动原 Core。

### 步骤 2：建立父子成对验证结构
- 评测里为每个专家建"父版本"（能力更弱，如工具更少），父/子各自跑同一批验证题；
- 证据带 `parent_id` 指向父节点，让 `BenchmarkLab._boundary()` 的 parent_items 非空。

### 步骤 3：四组对照跑全量
- A 固定根 / B 线性（只留最新）/ C 分支但不路由 / D 指纹路由+晋升；
- 指标：D vs C 路由净收益、A/B/D 遗忘回退、Wilson 区间、单任务成本。

## 三、工作量与风险（诚实）

- 步骤 1 触及 `YoAiAgent.astream` 的工具注册时序，是本轮最大的代码改动，
  需新增测试验证"白名单确实限制了工具调用"。
- 步骤 2 评测适配器要大改（成对节点 + parent_id 传播）。
- 步骤 3 全量 4 组 × 500 题，约 1.5-2 小时（额度无限，可接受）。
- **风险**：即便专家有了工具差异，LongMemEval 的 oracle 评测（一次性喂历史）下，
  工具查询未必比直接读历史更强——真实收益要在 retrieval 设置下才明显。
  可能需要把进化对照也切到 retrieval 模式，进一步加大工作量。

## 四、降级选项（如果只想快速要结论）

- **降级 A**：把"当前四组无差异（66.7% 持平）"作为诚实实验结论写入报告，
  说明"骨架就绪但专家能力未接线，暂无可测路由收益"，停止深挖。
- **降级 B**：只做步骤 1（白名单生效），用小样本验证"带工具专家 vs 裸答"是否有分数差，
  有差再决定要不要继续步骤 2/3；没差就直接得到"路由无收益"结论。
  这是**成本最低、信息量最大**的一步——建议如果继续，就从这里切入。

## 五、补充审查（2026-11-22 续）：发现更根本的场景错配

用户选"给专家真实能力差异"后，我继续追查白名单如何生效，又发现两层：

1. **工具白名单当前完全不生效**：`ExpertSpec.tools` 只用于路由打分
   （`router.py:148`），`ExpertModelProvider` 执行时**从未按白名单过滤工具**。
   换句话说，M1 里"专家带什么工具"是纸面配置，实际所有专家执行时工具集相同。
2. **更根本：场景错配**。oracle 评测是把全部历史直接喂给模型（长上下文 QA），
   模型已经看到了所有信息——此时"让专家查工具读历史"没有意义，工具查询在 retrieval
   模式下才有收益。所以即便白名单生效，在 oracle 框架里也测不出工具差异的价值。

要在 oracle 里做出能力差异，只能靠 prompt_suffix——而我们已经实测四组 prompt_suffix
差异导致成绩完全相同（66.7%）。

## 六、最终判断（诚实，停止深挖）

连续审查 6 层（验证入口→节点id→父子对照→白名单未接线→场景错配），每一层都是真实缺口。
继续往下做，需要：①改 YoAiAgent 工具过滤时序 ②切评测到 retrieval 模式 ③建父子成对样本
④四组全量——这是一个完整的小项目，且**最终能否测出收益仍不确定**（retrieval 下工具确实
有收益，但那已在记忆层实验里测过，与"进化路由"是否有关是另一个问题）。

**我的结论：在当前阶段，进化对照不具备产出可信结论的条件。** 与其堆一个骨架未通、
场景错配的实验得到假数据，不如把这次审查本身作为诚实成果：

- **已交付**：`bench/run_evolution_ab.py`（四组评测框架，节点 id 已修正）、
  验证样本入口修复（0→120 条）、全链路缺口文档（本文）。
- **诚实结论**：YoAi 进化机制 M0-M2 骨架完整，但"专家能力未接线 + 验证闭环未成 +
  oracle 场景错配"三处未通，当前跑 A/B/C/D 得到的是四组持平（66.7%）——
  这反映"当前配置无路由收益"，不是评测能证明进化有效。
- **真正该做**：若要做进化对照，先补专家能力接线（白名单生效）并把评测切到 retrieval，
  这是一个独立的新项目，建议单独立项、不与本轮捆绑。

不再逐层追问式深挖——这是建立在对代码真实状态核对后的收敛判断。
